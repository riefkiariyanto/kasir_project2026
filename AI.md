## 1. Ringkasan Aplikasi

Aplikasi kasir Flutter (`kasir_2026`) untuk bisnis nail art/salon kuku, dengan dua peran pengguna:

- **Admin** — login pakai username/password (`admin`/`admin`), masuk ke dashboard manajemen.
- **Pegawai** — tanpa login, cukup tekan tombol "Masuk sebagai Pegawai", langsung masuk ke halaman kasir untuk transaksi harian.

Seluruh halaman utama mendukung **dark mode & light mode** (toggle manual via ikon matahari/bulan di tiap AppBar, default light) — lihat §2 (`AppColors`), §5.18, dan §9.

**Target device: Android low-end diprioritaskan** (user eksplisit: "aplikasi difokuskan pengguna Android"). Implikasi: hindari animasi implisit (`Animated*`) yang tidak esensial secara UX, terutama di halaman admin (lihat §5.45) — kalau menambah interaksi baru yang "kelihatan bagus" tapi butuh animasi, pertimbangkan dulu apakah versi instan/tanpa animasi cukup sebelum menambah `AnimatedContainer`/`AnimationController` dkk.

Status build saat ini: `flutter analyze` bersih (0 issue), semua test (`flutter test`) lulus.

## 4. Fitur per Halaman

### 4.1 Login (`LoginPage`)
- Background foto (`assets/images/bg_login.webp`) **diputar 90° ke kiri** (`RotatedBox(quarterTurns: 3)`) dengan overlay gradien gelap.
- Form login (username/password) dalam panel translusen (bukan blur — demi performa di HP spek rendah).
- Tombol **"Masuk sebagai Pegawai"** di bawah form, dipisah divider "atau" — langsung ke `/cashier` tanpa validasi.
- Kredensial salah → dialog glassmorphism ("Login Gagal" / pesan error), bukan lagi SnackBar.

### 4.2 Dashboard Admin (`AdminDashboardPage`)
Topbar sama gayanya dengan `CashierPage` (hamburger custom kiri padding 10px, `BrandTitle` tengah, ikon pesan kanan padding 10px), plus `AdminDrawer` sendiri dan **`AdminBottomNav`** (bottom nav khusus admin, bukan reuse `CashierBottomNav` lagi).

**`AdminBottomNav`** (5 tab, style pill mengambang sama seperti `CashierBottomNav`):
| Index | Tab | Perilaku |
|---|---|---|
| 0 | Home | inline — `_AdminHomeTab` |
| 1 | Dashboard Laporan | push `/admin/reports` (`_navIndex` TIDAK berubah, sama seperti pola "Transaksi" di `CashierBottomNav`) |
| 2 | Kelola Katalog | push `/admin/catalog` (`_navIndex` TIDAK berubah) |
| 3 | Riwayat Pemesanan | inline — `OrdersList(orders: OrderRepository().fetchAll())`, widget publik yang SAMA dipakai tab "Pesanan" di `CashierPage` |
| 4 | Data Pegawai | push `/admin/employees` (`_navIndex` TIDAK berubah, sama pola dengan index 1/2) |

- **Beranda admin** (`_AdminHomeTab`): banner promo + grid menu cepat 4 item (`_AdminQuickMenuGrid`: Dashboard Laporan, Riwayat Transaksi → tab index 3, Kelola Katalog, **Data Pegawai → push `/admin/employees`**) + grid kategori (reuse `CategoryGrid` dari fitur cashier).
- **`AdminDrawer`**: Dashboard Laporan → push `/admin/reports`, Kelola Katalog → push `/admin/catalog`, Riwayat Transaksi → callback `onOpenOrders` (pindah ke tab index 3), **Data Pegawai → push `/admin/employees`**, Pengaturan → masih `showComingSoonDialog`, Logout. Constructor `AdminDrawer` wajib diberi 3 callback: `onFeatureTap` (kini cuma dipakai "Pengaturan"), `onOpenTransaction` (belum dipakai di body — dead param peninggalan drift, jangan heran), `onOpenOrders`.
- **`AdminCatalogPage`** — CRUD produk sungguhan lewat `ProductRepository.add/update/delete` (dialog editor per produk). Ini membuat `ProductRepository` **tidak lagi hanya data statis** — sekarang punya `static final List<Product> _products` yang bisa dimutasi, sehingga perubahan admin di sini akan langsung terlihat di katalog `TransactionPage` (repository dibagi lewat backing store static, sama seperti pola `OrderRepository`, lihat §4.4).
- **`AdminReportsPage`** — kartu ringkasan (`_ReportCard`) dan breakdown kategori (`_CategoryBarRow`, sekarang bar chart proporsional) dihitung LANGSUNG dari `OrderRepository.fetchAll()`, bisa difilter per tanggal lewat `showDatePicker` (lihat §5.39). Sudah jadi `StatefulWidget` (dulu `StatelessWidget`) dengan `orderRepository` sebagai constructor param (default `const OrderRepository()`, pola sama dengan halaman admin lain).
- **Tab "Riwayat Pemesanan"** — **menggantikan** `AdminTransactionsPage` yang dulu dummy 3 baris hardcode (sudah dihapus). Sekarang langsung baca `OrderRepository.fetchAll()` yang sama dipakai tab "Pesanan" `CashierPage` — jadi begitu pegawai checkout, order otomatis muncul juga di sini.
- **`AdminEmployeesPage`** (route `/admin/employees`, **BARU**) — CRUD akun kasir lewat `EmployeeRepository.add/update/delete`, mengikuti pola `AdminCatalogPage` persis (list `Card`+`ListTile` + FAB tambah + dialog editor `AlertDialog`). Tiap baris tampilkan nama + PIN (plain text, bukan mask — ini tool back-office, bukan layar publik). Validasi saat simpan: PIN harus persis 6 digit, dan PIN tidak boleh sama dengan pegawai lain (`EmployeeRepository.findByPin` dicek terhadap id yang sedang diedit, supaya edit pegawai yang sama dengan PIN tetap tidak dianggap duplikat).

### 4.3 Beranda Kasir (`CashierPage`)
Layout meniru mockup nail-art salon:
- AppBar putih: ikon hamburger custom (buka drawer, bukan `leading` bawaan Scaffold) di kiri, judul "Nail Art" (font brand) di tengah, ikon pesan di kanan. Padding kedua ikon **10px** dari tepi (disamakan dengan padding internal `CategoryCard`) — kalau nanti diminta "geser tombol topbar" lagi, ubah `EdgeInsets.only(left/right: ...)` di `leading`/`actions` pada `cashier_page.dart`.
- `TransactionPage` memakai AppBar dengan gaya identik (brand title + ikon pesan), tapi TIDAK diberi `drawer:` sehingga Flutter otomatis menampilkan tombol back (bukan hamburger) — dengan begitu tombol kembali tetap ada meski gaya topbar disamakan.
- Banner promo (placeholder abu-abu, rasio 6.5:1 — dibuat kecil sesuai permintaan).
- Grid kategori (Manicure, Pedicure, Nail Art, Extension, Gel Polish, Refill, Perawatan, Aksesori, Paket Hemat) — ukuran kartu diatur oleh `maxCardWidth` (saat ini 168px).
- **Bottom nav mengambang** (floating pill gelap, `extendBody: true`) dengan 4 tab: Beranda (index 0), Transaksi (index 1, push `TransactionPage`), **Pesanan (index 2, tab inline — lihat di bawah)**, Profil (index 3, masih `_ComingSoonTab`).
- **`CashierDrawer`**: Transaksi Baru → `onNewSale` (push `TransactionPage`), **"Riwayat Pemesanan" → `onOpenOrders` (pindah ke tab index 2, BUKAN dialog "coming soon" lagi)**, Logout. Constructor `CashierDrawer` cuma butuh 2 callback sekarang (`onNewSale`, `onOpenOrders`) — param `onFeatureTap` yang dulu ada sudah **dihapus** karena jadi dead code (tidak ada lagi tile yang memakainya).
- Tap banner/kategori/tombol drawer "Transaksi Baru"/tab "Transaksi" → semuanya membuka `TransactionPage`.

**Tab "Pesanan" (index 2)** — riwayat pesanan yang sudah checkout, ditampilkan inline (bukan halaman terpisah), sama seperti pola tab "Beranda". Memakai widget publik **`OrdersList`** (`features/cashier/presentation/widgets/orders_list.dart`) — widget yang SAMA juga dipakai tab "Riwayat Pemesanan" di `AdminDashboardPage` (lihat §4.2), jadi kalau mau ubah tampilan list order, cukup edit satu file ini, otomatis berlaku di kedua halaman:
- Sumber data: `OrderRepository().fetchAll()` — terurut terbaru dulu.
- Kosong → empty state internal `OrdersList` (ikon struk + teks "Belum ada pesanan").
- Ada isi → list `OrderCard` (ikon metode bayar, invoice id, waktu + jumlah item, total) dengan `AppColors.cardShadow` — gaya konsisten dengan kartu produk/kategori di §5.7.
- Tap kartu → `OrderDetailDialog.show()`: rincian item (`nama xqty` + subtotal per baris), waktu, metode pembayaran, total.
- **`TransactionPage._checkout()` yang menulis ke `OrderRepository`** setelah PIN diverifikasi benar dan sebelum keranjang dikosongkan — jadi begitu pegawai selesai bayar, order langsung muncul di tab Pesanan ini DAN di tab "Riwayat Pemesanan" admin (satu sumber data yang sama).

### 4.4 Halaman Transaksi / POS (`TransactionPage`)
Layout 2 kolom (berdampingan jika lebar layar ≥700px, bertumpuk jika sempit):

**Panel kiri — Katalog (flex 5 / lebar, flex 4 / sempit):**
- Kolom pencarian real-time by nama produk.
- Filter kategori (chip horizontal scroll + "Semua").
- Grid produk (`maxCrossAxisExtent: 200`) — kartu gambar placeholder + badge tag opsional (mis. "Custome") + nama + harga.
- Scrollable dengan padding bawah 96px agar item terakhir tidak tertutup bottom nav mengambang.

**Panel kanan — Keranjang (flex 2), gaya minimalis-elegan, "mengambang" dengan `AppColors.cardShadow`:**
- Header: "Keranjang (n)" — teks polos, tanpa gradien/badge warna.
- **Selector metode pembayaran (QRIS / Tunai)** — 2 tombol segmented di ATAS daftar item (bukan bottom sheet). Terpilih = latar primary solid + ikon putih.
- Daftar item (`CartItemTile`, ukuran diperbesar +15% dari revisi awal): baris flat dipisah garis tipis, nama produk + subtotal abu-abu, stepper kuantitas (lingkaran outline tipis +/−), **ikon hapus (trash) di ujung kanan** untuk menghapus item langsung dari keranjang tanpa perlu menurunkan kuantitas ke 0.
- Total & tombol **"Bayar"** — solid warna primary, nonaktif jika keranjang kosong ATAU metode pembayaran belum dipilih.
- Bottom nav mengambang juga muncul di halaman ini (tab "Transaksi" aktif; tab "Beranda" → pop kembali ke `CashierPage`).

**Alur checkout (2 tahap, sekarang multi-pegawai):**
1. Tap "Bayar" → membuka **`OrderVerificationDialog`** ("Verifikasi Pesanan"): menampilkan ulang daftar item (widget `CartItemTile` yang SAMA dengan panel keranjang — termasuk stepper +/− dan tombol hapus, keduanya masih bisa dipakai untuk mengedit pesanan di dalam dialog ini, langsung memutasi `CartController` yang sama), total, metode pembayaran, dan **input PIN kasir 6 digit**.
2. PIN diverifikasi lewat **`EmployeeRepository.findByPin(pin)`** — bukan cocokkan ke satu PIN generik lagi. Kurang dari 6 digit atau PIN tidak cocok dengan pegawai manapun → error inline "PIN salah, coba lagi", dialog tetap terbuka untuk dicoba ulang. PIN cocok → `OrderVerificationDialog.show()` mengembalikan objek `Employee` yang teridentifikasi (bukan `bool` lagi), dialog tertutup, **order dicatat ke `OrderRepository` DENGAN `cashierName: employee.name`**, keranjang dikosongkan, dialog "Pembayaran berhasil · <metode>" muncul. Tombol "Batal" menutup tanpa memproses pembayaran/tanpa mencatat order (tapi perubahan qty/hapus yang sempat dilakukan di dalam dialog TETAP tersimpan di keranjang, karena langsung memutasi `CartController`).
3. Jika semua item dihapus di dalam dialog (keranjang jadi kosong), tombol "Konfirmasi & Bayar" otomatis nonaktif dan menampilkan pesan keranjang kosong.
4. **Nama kasir yang checkout ditampilkan** di `OrderCard` (subtitle kecil, baris ke-3) dan `OrderDetailDialog` (baris "Kasir") — jadi riwayat pesanan sekarang bisa dilacak siapa yang memprosesnya.

**Data:**
- `ProductRepository` — backing store `static final List<Product> _products`, sekarang punya `add/update/delete` (dipakai `AdminCatalogPage`) selain `fetchAll()` — jadi SUDAH terhubung antara admin dan katalog kasir (satu sumber data yang sama), meski masih in-memory (hilang saat app di-restart, bukan database).
- `CartController` (ChangeNotifier) — kelola tambah/kurang/hapus (`remove()`) item + hitung total. Dipakai bersama oleh `CartPanel` dan `OrderVerificationDialog` (instance yang sama, bukan salinan).
- **`EmployeeRepository`** (menggantikan `EmployeePinRepository` yang sudah dihapus) — backing store `static final List<Employee> _employees`, CRUD penuh (`add/update/delete`) dipakai `AdminEmployeesPage`, plus `findByPin(String pin) -> Employee?` dipakai `OrderVerificationDialog` untuk mengidentifikasi kasir saat checkout. **Sudah di-seed 2 pegawai dummy**: Siti Aminah (PIN `123456`) dan Budi Santoso (PIN `654321`) — jangan hapus tanpa mengganti test yang bergantung pada PIN ini (lihat §6). `pinLength = 6` konstanta statis.
- `OrderRepository` — backing store `static final List<Order> _orders` (pola sama seperti `ProductRepository`: instance baru tetap berbagi data yang sama). **Sudah di-seed 5 order dummy** (`INV-001`..`INV-005`, waktu relatif ke `DateTime.now()` saat app start, kombinasi QRIS/Tunai, total 85rb–175rb, **masing-masing punya `cashierName`** — alternasi Siti Aminah/Budi Santoso) supaya tab "Pesanan"/"Riwayat Pemesanan" tidak kosong saat pertama dibuka — jangan dihapus tanpa diganti kecuali user minta orders tab benar-benar kosong di awal. `nextId()` generate id `INV-00N` sekuensial (lanjut dari `_orders.length`, jadi order sungguhan pertama otomatis jadi `INV-006`). Diisi juga oleh `TransactionPage._checkout()`, dibaca oleh tab "Pesanan" `CashierPage` DAN tab "Riwayat Pemesanan" `AdminDashboardPage` (satu sumber data, lewat widget publik `OrdersList` — lihat §4.2/§4.3).
- `CurrencyFormatter.rupiah()` — format manual "Rp45.000" tanpa dependency `intl`.
- **`RouteResults`** (`core/routing/route_results.dart`, **BARU**) — konstanta sinyal hasil `Navigator.pop()` lintas halaman (bukan teks user-facing, jadi sengaja dipisah dari `AppStrings`). Saat ini cuma `openOrders`: dipakai `TransactionPage` untuk memberi tahu pemanggilnya (`CashierPage` ATAU `AdminDashboardPage`, keduanya `await` hasil `pushNamed(AppRoutes.transaction)`) supaya berpindah ke tab riwayat pesanan setelah pop, alih-alih menampilkan "coming soon" (lihat bugfix di §5.16).

## 5. Desain / UI-UX — Riwayat Keputusan Penting

Beberapa keputusan desain sempat bolak-balik sesuai permintaan user — dicatat di sini supaya tidak diulang tanpa sadar:

1. **Blur/glassmorphism dihindari di tempat yang sering di-repaint** (background login, panel keranjang) demi performa HP spek rendah — `BackdropFilter` mahal karena `saveLayer` per frame. Tapi dipakai di `app_dialog.dart` karena dialog jarang repaint (muncul sesekali, bukan elemen yang terus update).
2. **Warna keranjang sempat dibuat gradien-warni (pink/ungu/hijau)**, lalu user minta ubah ke **minimalis-elegan** (putih + garis tipis abu-abu + 1 warna aksen primary). Jangan kembalikan ke gradien kecuali diminta ulang.
3. **Tombol QRIS/Tunai sempat berupa bottom sheet terpisah**, lalu dipindah ke bagian atas panel keranjang atas permintaan user. File `payment_method_sheet.dart` sudah **dihapus** (jangan dibuat ulang kecuali diminta).
4. **SnackBar untuk pesan (error login, "fitur belum tersedia") diganti dialog** (`showAppDialog` / `showComingSoonDialog`) — tampilan lebih konsisten dan modern.
5. **Ukuran komponen kasir (banner, kartu kategori, bottom nav, padding halaman) berkali-kali disesuaikan** — jika ada permintaan "perbesar/perkecil X", cek dulu konstanta yang relevan (biasanya satu angka: `aspectRatio`, `maxCardWidth`, `maxCrossAxisExtent`, padding horizontal) sebelum menulis ulang widget dari nol.
6. **Font "Nail Art" masih pakai serif italic bawaan sistem**, bukan font script asli seperti di mockup — user belum menyediakan file font atau menyetujui penambahan `google_fonts`.
7. **Efek 3D/shadow (`AppColors.cardShadow`) dipakai konsisten** di panel katalog, panel keranjang, `ProductTile`, `CategoryCard`, dan `ProductSearchField` — sengaja pakai `BoxShadow` biasa (bukan `BackdropFilter`) karena murah untuk elemen yang sering repaint. Kalau nanti ada permintaan "buat 3D juga" pada komponen lain, pakai konstanta yang sama, jangan bikin shadow custom baru kecuali diminta beda.
8. **Checkout sekarang 2 tahap** (dialog verifikasi + PIN pegawai) — jangan disederhanakan kembali ke 1 klik langsung kecuali user minta eksplisit, karena ini permintaan keamanan/verifikasi yang disengaja.
9. **Padding tombol topbar (`cashier_page.dart`) sempat disetel beberapa kali** (16 → 20 → 32 → akhirnya 10, disamakan dengan padding internal `CategoryCard`) — nilai final 10px, jangan diasumsikan angka lain dari draft sebelumnya.
10. **`OrderRepository` dan `ProductRepository` memakai pola "singleton via static backing list"**: constructor `const`, tapi field data-nya `static final List<...>` di dalam class — jadi `const OrderRepository()` yang dibuat di file/halaman berbeda tetap membaca/menulis data yang SAMA (bukan instance terpisah). Kalau menambah repository baru yang datanya perlu dibagi antar halaman (misal nanti "riwayat aktivitas pegawai"), ikuti pola yang sama, jangan pakai `InheritedWidget`/state-management baru hanya untuk satu kasus kecuali user minta.

Sekarang: `surface` abu gelap kebiruan `0xFF232326` (bukan hitam), `panelSurface`/kartu `0xFF2E2E32` (sengaja lebih terang dari `surface` untuk kesan elevasi lembut, bukan cuma beda alpha), `onSurface` off-white `0xFFE7E7EA` (bukan putih murni — mengurangi silau), `primary` ungu terang `0xFFC4B0EA`, dan `cardShadow` dark alpha diturunkan (`0x33`/`0x1F`, dulu `0x66`/`0x40`) supaya bayangan tidak terlihat berat di atas latar yang sudah gelap. `AppTheme.dark.scaffoldBackgroundColor` disamakan ke `0xFF232326`. **Kalau user minta "lebih gelap lagi" atau "lebih terang lagi" ke depannya, cukup geser value hex ini di `app_colors.dart` — jangan ubah arsitektur getter/notifier-nya.**

## 7. Belum Dikerjakan / Diketahui Terbatas (jangan diklaim selesai)

- **`AdminReportsPage` SUDAH terhubung ke `OrderRepository`** (lihat §5.39) — bukan lagi item "belum dikerjakan". Yang masih terbatas: filter tanggal cuma satu tanggal spesifik (bukan rentang tanggal/date range), dan breakdown kategori cuma berupa bar chart sederhana custom-widget (bukan library chart sungguhan) — kalau nanti user minta jenis chart lain (garis/pie) atau filter rentang tanggal, itu perluasan baru, bukan sekadar bugfix.
- Menu admin "Pengaturan" masih placeholder (`showComingSoonDialog`) — belum ada halaman fungsional. (**"Data Pegawai" SUDAH selesai** — lihat §4.2 `AdminEmployeesPage`.)
- `CategoryRepository` sekarang punya `add()` (dipakai dropdown kategori `AdminCatalogPage`, lihat §5.35) tapi BELUM ada `update`/`delete` kategori — beda dengan `ProductRepository`/`EmployeeRepository` yang sudah CRUD penuh.
- Data (`ProductRepository`, `OrderRepository`, `EmployeeRepository`) semuanya in-memory per sesi aplikasi — hilang saat app di-restart, tidak ada persistensi (database/API/local storage).
- PIN kasir yang dipakai saat checkout **PIN mentah tidak disimpan di `Order`** (cuma `cashierName` hasil identifikasi) — jadi kalau butuh audit trail yang lebih ketat (mis. deteksi PIN dicoba berkali-kali/brute force), masih perlu logging terpisah.
- Pembayaran QRIS/Tunai hanya simulasi UI (tidak ada integrasi payment gateway atau QR code sungguhan).
- **`AdminEmployeesPage` menampilkan PIN dalam bentuk plain text** (bukan hash/mask) di daftar dan field edit — wajar untuk tool back-office kecil seperti ini, tapi kalau nanti butuh keamanan lebih (mis. multi-admin dengan hak akses berbeda), PIN sebaiknya di-hash dan tidak ditampilkan ulang setelah disimpan.
- Permintaan **"keranjang bisa di-minimize/diperkecil ke samping kiri"** sempat diajukan user lalu di-interrupt sebelum dikerjakan — **belum diimplementasikan**.
- Belum ada state management global (Provider/Riverpod/Bloc) — semua state masih `setState` + `ChangeNotifier` lokal per halaman, plus pola "static backing list" untuk data yang perlu dibagi lintas halaman (lihat §5.10).
